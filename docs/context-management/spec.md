# Context Management Spec

## 背景

MewCode 当前把完整会话历史传给模型。会话历史包括用户消息、assistant 回复、assistant 发起的工具调用以及工具结果。随着 agent 多轮执行，Token 增长的主要来源通常是工具结果，例如文件读取、搜索结果、命令输出和远端工具返回的大块文本。现有工具虽然会做单次输出截断，但长期会话中大量工具结果仍会累积，最终可能逼近模型上下文窗口并导致请求失败、回复质量下降或 agent 无法继续执行。

本章为 MewCode 增加上下文管理能力：在每次模型请求前先做轻量预防，把过大的工具结果转为本地文件引用；再在整体历史逼近上下文窗口时做重量兜底，用无工具 LLM 调用生成结构化摘要，压缩较早历史并保留近期原文。系统必须优先保留用户原始表达，只有在整体上下文必须兜底压缩时，才把较早用户消息纳入摘要。

## 目标

- 让 MewCode 在有限上下文窗口内持续完成长时间、多工具、多轮任务。
- 优先压缩工具结果，尽量不改写用户原始消息和近期对话。
- 对单个过大工具结果和同一批工具结果合计过大分别做轻量预防。
- 在整体会话逼近上下文窗口上限时，生成结构化摘要压缩较早历史，并保留近期原文尾部。
- 手动和自动压缩使用不同安全余量：自动触发保留 13K token，用户手动触发保留 3K token。
- 摘要失败不能形成死循环；连续失败 3 次后自动熔断。
- 压缩后的会话必须明确提示模型：摘要不是代码和工具输出的精确来源，需要细节时重新读取引用文件。

## 功能需求

- F1: 每次模型请求前执行上下文预处理
  系统在每次向 provider 发起模型请求之前执行上下文预处理。预处理顺序固定为：先执行轻量预防，再估算整体会话 token 是否需要重量兜底。预处理不得改变当前用户刚提交的原始文本含义，不得在压缩失败时吞掉用户请求。

- F2: 使用近似 token 估算
  系统使用近似 token 估算，不引入精确 tokenizer。估算优先锚定最近一次 API usage 中的输入 token；有 usage 时只对上次请求后新增或变更的会话内容按字符数估算增量。没有 usage 时，按当前会话序列化后的字符数估算总量。估算结果用于触发压缩，不作为计费或精确统计依据。

- F3: 轻量预防压缩单个大工具结果
  当单个工具结果的序列化体积超过系统定义的单结果阈值时，系统把该工具结果的完整可回灌内容存入本地文件，并在会话中保留一个有界预览。预览必须包含工具名、调用 id、成功或失败状态、摘要、耗时、是否截断、本地文件路径，以及足够判断下一步行动的短内容片段。预览必须保持原 tool result 的协议位置和 tool_call_id，使 provider 仍能看到合法的工具调用结果。

- F4: 轻量预防压缩同一批过大的工具结果
  当同一轮 assistant 工具调用对应的一批工具结果合计超过系统定义的批结果阈值时，系统按工具结果序列化体积从大到小依次存盘并替换为预览，直到该批结果合计低于阈值，或该批中所有可存盘结果都已替换为预览。已被单结果规则压缩过的结果计入合计时只计算预览体积。

- F5: 工具结果本地存储
  存盘位置位于项目本地、默认被 Git 忽略的 MewCode 私有目录下。每个存盘文件必须能还原该工具结果的完整 payload，并包含元数据：创建时间、工具名、调用 id、结果状态、原始估算 token、预览估算 token、会话轮次或序号。文件路径写入会话预览，供模型后续通过读文件工具重新获取细节。本章不要求实现自动清理、压缩包归档或跨项目同步。

- F6: 重量兜底触发
  轻量预防完成后，系统估算当前会话加上本次预计输出和安全余量是否逼近上下文窗口上限。自动触发时安全余量为 13K token；用户手动触发时安全余量为 3K token。若估算显示上下文仍有足够空间，自动流程不做重量兜底；手动流程可以在用户明确触发时执行一次重量兜底。

- F7: 重量兜底保留近期原文
  重量兜底只压缩较早历史，近期尾部必须原文保留。从会话尾部向前累计，至少保留约 10K token 的原文，且至少保留最近 5 条会话项；如果为保持 provider 工具调用协议合法需要保留完整 tool_call/tool_result 批次，则继续向前扩展保留范围。近期尾部中的用户消息、assistant 回复、工具调用和工具结果不得被摘要改写。

- F8: 重量兜底生成结构化摘要
  系统用 LLM 对被压缩的较早历史生成结构化摘要。摘要必须按固定部分组织，至少包括：当前目标与用户意图、已完成工作、关键决策与约束、重要文件和代码状态、工具调用证据与本地存盘引用、未完成事项、风险与注意事项。摘要必须尽量区分用户原话、assistant 推断和工具观察结果。

- F9: 摘要调用禁止工具
  摘要调用必须明确禁止模型调用任何工具，并且实际请求不得携带工具定义。摘要 prompt 必须要求模型先进行临时分析草稿，再产出正式摘要；系统只保留正式摘要，临时草稿不得进入会话、不得落盘、不得展示给用户。若模型返回工具调用、空摘要、缺失必要结构或 provider 报错，该次摘要视为失败。

- F10: 压缩后插入边界消息
  重量兜底成功后，系统用一条摘要消息替换被压缩的较早历史，并在摘要与近期原文之间插入边界消息。边界消息必须明确说明：早期详细消息和工具输出已被压缩；摘要只供定位和连续性使用；需要文件、命令输出或工具结果细节时必须重新读取摘要中列出的本地文件或项目文件，不能根据摘要脑补代码和输出。

- F11: 用户手动触发压缩
  用户可以通过明确命令手动触发压缩。手动命令不作为普通用户请求加入会话，不发送给 agent 执行。手动触发时先执行轻量预防，再以 3K token 安全余量尝试重量兜底，并向用户展示成功、无需压缩或失败原因。若当前没有可用 provider 执行摘要，手动压缩必须失败并给出可理解提示。

- F12: 摘要失败熔断
  系统记录连续重量兜底摘要失败次数。连续失败 3 次后，本会话自动重量兜底熔断，不再在请求前反复尝试摘要，避免死循环。熔断后轻量预防仍继续执行。用户手动触发时，系统应提示摘要已熔断以及最近失败原因；除非用户开启新会话或显式重置压缩状态，否则不再自动调用摘要。

- F13: 不破坏 provider 协议语义
  压缩后的会话历史必须保持 provider 可接受的消息结构。系统不得留下孤立的工具调用或孤立的工具结果；不得把工具结果移动到不属于原调用批次的位置；不得让 OpenAI 或 Anthropic 的工具结果消息缺失必要 id。重量兜底切分历史时必须按完整会话项和完整工具批次切分。

- F14: 可观测压缩事件
  每次轻量或重量压缩都应产生可展示的事件或通知，包含压缩类型、压缩前后估算 token、存盘文件数量、摘要是否成功、熔断状态等关键信息。通知面向用户简短展示，不暴露隐藏草稿，不泄漏存盘文件以外的敏感内容。

## 非功能需求

- N1: 安全性
  工具结果存盘目录必须位于本地项目私有目录，并默认不进入版本控制。系统不得因为压缩而把密钥、命令输出或工具结果复制到公开文档、日志或可提交文件中。

- N2: 稳定性
  压缩失败不得导致当前 agent turn 崩溃。轻量压缩文件写入失败时，该结果保持原样并记录失败；重量摘要失败时，本次请求可以继续按未摘要历史发送，若仍超过上下文窗口则向用户返回可理解错误。

- N3: 兼容性
  上下文管理应在 Anthropic、OpenAI 和 OpenAI-compatible provider 下保持一致的会话语义。provider 适配层可以继续接收统一的会话项和工具结果，不需要知道某个工具结果原先是否被存盘。

- N4: 性能
  轻量预防只做本地序列化、估算和文件写入，不调用 LLM。重量兜底仅在触发条件满足或用户手动触发时调用 LLM，不得每轮无条件摘要。

- N5: 可测试性
  阈值、估算器、存盘根目录和摘要 provider 必须能在测试中替换或注入，以便用小型会话稳定验证触发、存盘、摘要、熔断和协议合法性。

- N6: 范围克制
  本章不引入精确 tokenizer，不实现机器学习式摘要策略优化，不实现跨会话长期记忆，不实现 artifact 自动清理策略，不实现向量检索，不改变现有工具权限模型。

## 不做的事情

- 不对每个模型接入专用 tokenizer，也不保证估算 token 与 provider 账单完全一致。
- 不把用户近期原始消息改写成摘要；只有较早历史在重量兜底时会被摘要。
- 不让摘要调用使用任何工具、读取文件或访问外部资源。
- 不把工具结果存盘文件提交到 Git，也不在公开文档中复制这些文件内容。
- 不实现自动删除、压缩、迁移或同步存盘 artifact。
- 不实现跨会话长期记忆、项目知识库或向量数据库。
- 不改变工具权限、MCP 权限、文件沙箱或命令执行安全规则。
- 不新增机器学习模型来选择摘要策略。

## 验收标准

- AC1: 在一次 agent turn 发起模型请求前，系统总是先执行轻量预防，再判断是否需要重量兜底；当前用户请求仍原文保留。
- AC2: 当单个工具结果超过测试注入的单结果阈值时，会话中的该结果被替换为有界预览，完整 payload 写入本地文件，预览中包含可读文件路径和原 tool_call_id。
- AC3: 当同一批工具结果合计超过测试注入的批结果阈值时，系统按体积从大到小存盘替换，直到批结果估算低于阈值或无可替换结果。
- AC4: 存盘 artifact 位于 Git 忽略的本地私有目录，文件内容能还原工具结果 payload，并包含工具名、调用 id、状态和估算 token 元数据。
- AC5: 自动触发重量兜底时使用 13K token 安全余量；手动触发时使用 3K token 安全余量。
- AC6: 重量兜底成功后，较早历史被一个结构化摘要替代，近期尾部至少保留约 10K token 或最近 5 条会话项，并且不会切断工具调用/result 批次。
- AC7: 摘要正文包含固定部分：当前目标与用户意图、已完成工作、关键决策与约束、重要文件和代码状态、工具调用证据与本地存盘引用、未完成事项、风险与注意事项。
- AC8: 摘要调用的 provider 请求不携带工具定义；若 fake provider 返回工具调用或缺失结构，系统把该次摘要判定为失败。
- AC9: 摘要成功后，会话中出现边界消息，明确要求后续模型需要细节时重新读取文件，不得根据摘要脑补代码或工具输出。
- AC10: 用户输入手动压缩命令时，该命令不会加入普通对话历史，不会触发 agent 执行；UI 展示压缩结果或失败原因。
- AC11: 连续 3 次重量摘要失败后，系统进入摘要熔断状态；后续自动请求不再尝试重量摘要，轻量预防仍继续运行。
- AC12: 压缩后的 OpenAI 和 Anthropic 请求消息结构仍合法，不存在孤立 tool_call、孤立 tool_result 或缺失 tool_call_id 的工具结果。
- AC13: 没有 usage 信息时，系统仍可用字符估算触发压缩；有 usage 信息时，后续估算以最近 usage 为锚点并只估算增量。
- AC14: 轻量存盘失败或重量摘要失败时，系统不丢失原始会话项，并向用户或事件流提供可理解失败信息。
- AC15: 现有 agent loop、工具执行、权限模式、MCP 工具调用和 provider 流式输出测试继续通过；新增测试覆盖轻量压缩、重量摘要、手动触发、熔断和协议合法性。
